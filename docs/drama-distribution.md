# 主体发布方与同主体应用分发

TikTok 发布方在后台「主体管理」维护，每个应用绑定一个主体。各主体的 AppID、Client Key 和 Client Secret 单独保存；同剧的 Album、分集映射、审核和已选线上版本分别维护。VOD、草稿、原视频和直连线上目录继续共享。完整边界和迁移步骤见 [主体](subjects.md)。

主体管理响应只返回 `clientSecretConfigured`，不返回密钥。更新时相同发布身份的空密钥保留原值；更换发布身份必须提供新密钥，已有官方资产时禁止更换身份，只允许轮换 Secret。稳定 `publisher_owner_id` 保留历史归属，不能通过改名或后台选择改变。发布与授权每次从任务固定的主体读取凭据，不从应用列表猜测发布方。

同步入口冻结当前就绪内容，新剧使用选定主体发布方，版本记录保留实际拥有方和媒资空间。送审入口单独接收 `priority`。版本选择、上下架与应用授权分别在本次请求内完成，不通过发布或分发任务串联。

`drama_distributions` 以 `(drama_id, application_id)` 为唯一键，保存运营意图及平台确认事实。人工授权/撤权在请求内完成，不提交队列、不自动重试同步失败。拥有方随已选官方线上版本直接可用；十分钟应用策略对账处理停用、重新启用和上下架变化，保留人工撤权。

- `GET /admin/v1/dramas/{dramaID}/distributions`：短剧读取权限，只读本地关系。
- `PUT /admin/v1/dramas/{dramaID}/distributions/{applicationID}`：短剧分发权限（旧发布权限兼容），输入 `{"enabled":true|false}`；同一意图可明确重试。
- `POST /admin/v1/applications/{applicationID}/drama-authorizations`：同一权限，输入 `{"dramaIds":["201"]}`，同步逐项授权，成功返回 HTTP 200 / `authorizedCount`。先检查所有目标是否上线，调用期间已确认的授权不因后续失败而伪称回滚；失败后刷新可见各项实际结果。
- 官方授权使用拥有方凭据，目标应用 Client Key；新增授权确认 `auth_status=1`，撤权确认 `auth_status=2`。单次平台调用上限三十秒，短剧/关系锁防止相反操作交错。
- 撤权失败保留失败事实并移除本地访问权限；重复明确设置同一目标可收敛远端状态，不运行授权队列消费循环。
- 平台结果与消费者授权投影在同一 MySQL 事务提交；成功或本地撤权提交后失效目录缓存。新版本选择读取已确认授权关系，不覆盖并发撤权。

主体增量增加归属与投影，既有分发关系仍按应用保存；目标应用必须属于同一主体。自动化只使用隔离 MySQL、Redis 和模拟平台响应，不向真实平台发送请求。

## 已选版本的独立上下架（2026-10-11）

TikTok `album/update` 生成新版本，`review/submit` 审核指定版本，`album/online_version` 选择审核通过的版本，`album/status` 控制整个 Album 上下架。这四类操作不能合并成单一草稿状态。V1 已选时，V2 的草稿保存、同步、送审或审核通过都不替换 V1；管理员点击“更新上线”才将 V2 设置为线上版本并上架。

同步媒资、Album 创建/更新、送审、撤回、申诉提交、人工查询、版本选择和上下架全部在请求内完成同步调用。只有视频处理结果及审核/申诉结论通过后台查询等待；不自动送审或上线。失败在原冻结记录留档并直接返回，不排队重放同步写入。非幂等调用仍使用既有检查点防止结果未知时重复创建或提交。

`tiktok_release_records` 保存已选版本及确认的上下架状态，原冻结版本记录提供不可变内容。下架清除消费者可见指针，但保留版本、审核事实和分集映射；重新上线只恢复原选择并调用 Album status，不上传、同步或重新送审。版本选择和上下架串行；内容同步/审核保持独立。只有确认的上下架结果可以更新消费者线上指针；版本选择已成功但随后上架异常时保存已确认的选择并返回错误，避免本地误认旧版本仍被选中。

官方和直连下线均检查本渠道轮播和热播全部引用，含隐藏项及历史 `dramaIds`。官方在剧目锁内校验并调用平台；推荐新增也取得此锁，不留下下线后才新增的推荐。被引用返回友好提示，保留线上版本及审核状态。

“新内容待同步”仅比较 Album 实际字段：名称、简介、封面来源、语言、年份、连载状态、剧类型、标签及分集身份/顺序/标题/VID。首帧图、时长、分集本地简介与媒资技术状态不触发官方新版本；直连完整内容快照比较保持原规则。

主体升级需执行新增迁移。Mini `/api/v1/*`、`/api/v1/open/*` 和原播放器消费契约不变。

升级前排队的同步步骤及已失效请求租约在页面投影为人工待办，不改写原冻结记录或自动重发。活跃请求仍受修订与租约保护；未知写入只提供核对入口，真实媒体及审核查询继续等待平台。运行时只读取选定主体的权威上架记录，不从其他任务或其他主体推断已选版本。

## Album 分集映射与版本可见性（2026-10-12）

真实 `album/update` 首次写入返回的 `episode_id_map` 占位键为 `seq:1`、`seq:2` 等，既有分集则按传入的官方 Episode ID 匹配。适配器按这份实际合同解析，标识值始终保留字符串，并校验序号、完整性、唯一性及冲突；完整响应直接确认，不依赖紧随写入的查询。[官方文档](https://developers.tiktok.com/docs/en/media-asset-api-reference) 当前示例写为 `seq_1`，与本次真实调用不一致，不能据此覆盖已验证的合同；回归用例见 `internal/data/platform/tiktokmedia/album_mapping_test.go`。

实测首次更新成功后立即查询可能返回空版本列表，稍后才能读到 V1；后续更新也可能先返回新的 `current_version`，但列表仍只有旧版本。恢复核对须区分版本详情尚不可见与实际内容冲突：前者保留可再次查询的未知状态并记录 `latest_version_not_visible`，后者继续暂停。人工重试只查询原 Album 并核对冻结内容，不重发更新，不转为后台同步队列。
