# 服务器时间统一方案与旧版兼容

状态：**已实现，自动化与隔离数据库验证见文末；真实平台设备回归待验收。**

确认日期：2026-10-23（Asia/Shanghai）。涉及 `drama-server` 与 `drama-mini`，后台不需要新增配置或菜单。

## 已确定的业务口径

广告完成后，哪天收到请求就算哪天；日期按应用配置的时区计算，不按手机日期，也不直接使用服务器操作系统的当地日期。

- 展示确认与完播结算是两个独立事实，分别使用各自请求首次到达应用服务的时间。展示成功不能替代完播；只有 SDK 明确返回 `isEnded === true` 才申请奖励。
- 网络延迟或离线补报跨过午夜时，新事实属于服务器首次收到它的当天，不还原手机上的原观看日。
- 同一展示 `eventId`、奖励 `claimId` 的重试仍只对应原记录；重试跨日不改变原记录时间，不重复累计或发奖。
- 入剧规则的 `shown`／`completed` 计数模式保持各自含义，不能把展示计数统一改成完播计数。
- 历史记录、已经授予的权益与已经确认的统计不重新计算。

## Server 实现约束

### 请求时间与事实时间

在应用 HTTP 入口记录一次 UTC 接收时间，随请求 Context 传递。处理过程中不能反复读取当前时间来决定本次事实所属日期，避免请求在鉴权、数据库等待期间跨过午夜而改变口径。内部非 HTTP 入口通过同一个可注入业务时钟确定时间，便于测试。

旧包发送的 `occurredAt` 字段继续接收，合法格式的历史请求保持可解析；它不再决定广告业务确认是否成功，也不决定业务日归属。新版不需要提交手机时间才能完成确认。客户端时间若用于诊断，只能作为非权威信息，不能参与权益、日计数或播放许可判定。

不直接在每次重试中执行 `input.OccurredAt = now` 后沿用现有匹配条件。否则第二次请求的时间与原记录不同，会把正常重试判成冲突。存储必须在事务或唯一键冲突处理内完成：

1. 以可信应用、用户及 `eventId`／`claimId` 查找或插入。
2. 首次插入固定服务器接收时间；并发冲突后读取已存在记录。
3. 重试核对场景、广告位、剧目、剧集或奖励目标等不可变内容。同键改写业务目标仍拒绝。
4. 已存在记录返回原确认结果；不更新原时间，不占用新一天的次数，也不重复授予权益。

现有历史记录可能保存客户端时间。遇到这些记录的重试仍保留原时间，不在本次升级中迁移日期。

### 响应提供时间基准

在相关成功响应的公共包装层增加可选字段 `serverTime`，为生成该响应时的服务器 UTC 时间，使用 RFC 3339 格式。保持现有 `code`、`reason`、`message`、`data` 的类型及业务字段不变。

该字段用于计算响应内 `expiresAt`／`validUntil` 的剩余有效期，和请求接收时间职责不同，不能用响应生成时间覆盖广告事实时间。覆盖启动、播放许可、入剧广告状态、广告计数以及携带 VIP 状态的结算响应。

不修改 `/api/v1/*`、`/api/v1/open/*` 的路径结构，不增加版本请求头、客户端合同时钟模式或专用校时接口。不新增数据库字段、业务任务或迁移 SQL。

## Mini 实现约束

### 统一剩余有效期

在 HTTP 适配层接收 `serverTime`，把响应中的绝对有效期转换为当前页面内的单调时间截止点。示意：

```text
remainingMs = expiresAt - serverTime
deadline = requestStartedMonotonic + max(0, remainingMs)
```

以请求发起时的单调时间为基点可保守扣除本次往返耗时。实际提前刷新余量统一管理，不能在多个模块继续混用手机 `Date.now()`。该计算只用于缓存和刷新时机，不授予权益，也不替代服务器或 SDK 验证授权。

不修改设备系统时间，不把一次计算出的 `Date.now()` 偏移永久保存为权威时钟。切换账号、应用或重建页面时清理相关时间基准和旧主体响应。

### 各业务流程

- **VePlayer**：两个现有校验入口一起调整。保留 provider、VID、短期 Token、有效期格式及官方映射的校验；临近到期或已经失效时重新请求许可。真正的授权失败仍按原重试和错误提示处理，不能简单删除所有有效期检查。
- **VIP**：服务端 `active`、`validUntil` 及已确认权益是权威。客户端到期触发重新查询，不能仅因手机日期变化判定已购买／已领取的权益失效，也不能因手机慢而自行延长权益。领奖后迟到的旧状态仍不得覆盖新权益。
- **入剧广告**：服务端返回当日进度、门槛与 Offer。截止时重新查询，不自行用手机日期清零进度。刷新失败保留明确的恢复入口，不无限刷新，也不擅自判定达标。
- **前后台切换**：WebView 或设备休眠可能暂停计时器，不能假定单调计时器在所有设备后台都持续推进。回前台后刷新相关状态或重新验权，陈旧缓存不能直接产生新的播放或奖励决定。
- **统计与诊断**：耗时继续使用单调时钟；梳理现有客户端时间窗口是否造成指标或补报丢弃。诊断事实不能替代奖励账本，也不能把 SDK 成功回调解释为 TikTok 归因或结算成功。

## 旧版兼容与发布

1. 先发布 Server，再发布 Mini。旧 Mini 仍可使用原接口和原请求字段；新增响应字段不能变成旧客户端必填项。
2. Server 不再依据手机时间拒绝广告确认，可改善旧包的此类请求；旧包自身已有的 `Date.now()` 判断无法由服务端文档或新增字段消除，播放、VIP、入剧状态的客户端修复需要升级 Mini。
3. 新版不提供播放器自动回退，不改变官方与直连 provider 的选择，不改变广告完播证明、权限和 ClaimID 隔离。
4. 响应缺失或无法解析时间基准时，不把手机时间当作可靠替代。相关缓存按未确认处理并走已有受控刷新流程，不自行授予权益、不循环重试。
5. 可以单独回退 Mini；Server 新增的可选响应字段对旧包保持兼容。回退 Server 前须核对新版 Mini 对时间基准的依赖，不能把新版直连流量直接交给尚未升级的 Server。

## 实现说明与自动化验证

- `internal/pkg/requesttime` 在最外层 HTTP 入口固定接收时间；消费者 Handler 独立挂载时仍会建立相同边界。内部业务调用使用注入时钟，同一次调用链不会因等待依赖跨过午夜而改日。
- 展示幂等先读取原事实，再验证新展示所需的当前广告和目录资源。仓储在唯一键冲突后仅核对不可变内容，历史记录时间保持原值。领奖同键替换广告位、规则、剧目或目标集会拒绝，合法重试仍优先恢复原结算。
- VIP 同日领取按用户锁串行化。接收顺序与锁提交顺序不同的请求使用原授予时刻恢复同一来源权益，仍经过当前投影及撤销检查，避免因较早请求看不到稍后提交的授予而重复写入。
- Mini 的 `ServerClock` 为每个响应换算独立的单调截止点；账号变化及前后台边界会失效旧截止点和在途响应。播放授权保留统一的 5 秒提前刷新余量及 20 秒页面缓存期限。
- VIP 到期先标记待刷新，复用已有启动流程重新确认。失败保留已确认事实及手动重试入口，不能触发循环刷新、自动撤销或多拉广告；旧查询也不能覆盖较新的领奖结果。
- 待展示补报保留 48 小时，使用当前前台代次的服务器基准。旧记录没有可信排队时间时，取得基准后开始保留期；手机日期不参与清理，同键重试不重置保留期。此本地元数据不发送到 API。
- 全屏广告等待、失败退避与插屏间隔改用单调计时。Storage 只保存尝试标记；新页面有标记时保守等待一个配置间隔，不比较上一个页面的单调时间原点。
- 验证覆盖请求处理跨午夜、展示与完播分属两日、跨日／并发幂等、旧时间字段、超前／落后设备时钟、后台暂停、缺失基准、授权刷新、VIP 迟到覆盖及失败恢复。隔离 MySQL／Redis 验证展示、奖励、VIP、统计和旧接口消费；后台消费方无需修改业务代码。
- 发布顺序仍为先 Server 后 Mini；本次没有数据库迁移。

### 达标后仍保存事实：最终实现（2026-10-24）

- 展示和入剧完播各按原 `eventId`／`claimId` 保存到现有表，复用现有事务及唯一键。达到 N 后也保留有效事实，不再使用入剧写入上限参数或提前返回分支；没有新增表、字段、SQL、任务或独立达标状态。
- N 是是否继续要求观看的门槛。服务端返回当天当前范围的真实次数，允许超过 N；Mini 使用返回值放行，显示最多 N/N，既不自行加一，也不因为次数超出门槛继续拉广告。
- 原键重试优先恢复已有事实，保留首次确认请求的服务器接收时间；跨日回包仍给出今天的最新进度。新键首次到达则按当前服务器接收日计数。同键改写广告位、剧目等业务目标继续拒绝。
- 新服务端不再产生跳过落库的 `entry_satisfied`；有效入剧完播首次为 `granted`（201），重试为 `already_granted`（200）。Mini 保留旧 `entry_satisfied` 解析和结算附加状态缺省回退。原接口路径和请求字段不变，VIP、分集解锁的额度和权益发放不变。
- 入剧完播不会发放额外内容权益。升级后达标后的有效入剧完播也会纳入后台结算数；VIP、解锁权益计数不变。历史已落库时间不重写，升级前丢失的事实无法还原。
- 回归将原“达标后不增加记录”的断言替换为“每个不同有效键各记一次，同键只记一次”。覆盖两种播放器、入剧四种计数模式、达标后在途请求、跨日并发重试、旧字段消费、VIP 和分集发奖隔离，并验证数据库升级后的历史事实仍保留。

### 前台恢复与登录解耦（2026-10-24）

版本 123 真机验证中观察到两种不同现象：TikTok 原生“无法打开 TikTok Minis”发生在项目页面出现前，尚无日志证实根因；应用进入后台后返回，出现项目内请求超时，手动重试可恢复。不能把二者都归因于登录态丢失。

已定位的代码问题：VIP 开启时每次前台恢复都通过完整 Bootstrap 刷新权益，重复调用 TikTok 静默登录；登录只有 3 秒等待额度，HTTP 与 SDK 初始化计时也包含后台停留。当前修复如下：

- 新增 `GET /api/v1/me/ad-experience`，用现有 Bearer VisitorToken 查询 `monetization`、`vipState`、`vipOffer`，响应继续携带 `serverTime`。服务端按请求接收时间查询当天事实，不签发 Token、不调用 TikTok、不改变启动归因、不自动领取 VIP。响应禁止缓存。
- 原 Bootstrap 请求、响应字段和静默登录要求保持。启动与新查询共用同一个权益投影；旧 Mini 继续调用原接口。新 Mini 遇到旧服务端明确返回 404 时才回退原启动流程；其他失败保留原分类，不通过重新登录掩盖。
- 前台恢复使用新查询。查询返回明确的 401/unauthorized 时才沿用既有凭据恢复，恢复后仍校验应用和用户；普通网络故障不换号、不匿名降级。
- 后台取消的是在途的权益只读查询。再次前台恢复时重新读状态，取消与迟到响应不能覆盖新进度。广告结算继续使用原 ClaimID，切后台不重发或换键；有效期仍以新服务端响应为准。
- HTTP（含响应体）、SDK 初始化和静默登录只累计前台等待时间；登录额度由 3 秒调整为 15 秒。暂停计时不代表成功，不取消真实网络错误，也不自动重新拉广告。
- 无数据库、SQL、Admin 修改。部署顺序为 Server → Mini。TikTok 原生加载失败仍须结合容器网络/诊断日志和重新扫码验证；不能用本地测试通过宣称该平台现象已修复。

聚焦测试覆盖：前后台双信号、后台一分钟、设备日期跳变、登录迟到成功/真实超时、领奖响应体挂起、取消与监听释放、前台查询复用 Token、迟到响应隔离、旧服务端 404 回退、旧 Bootstrap 合同、鉴权错误分类和只读查询不发放权益。真实设备上运行的仍是版本 123，修复包尚未上传，新的服务端接口尚未部署。
