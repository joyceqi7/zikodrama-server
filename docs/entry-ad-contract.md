# 入剧广告与通用展示事实

## 策略与职责

`entry_rewarded_ad` 用两个配置维度组合四种场景，`requiredAdCount` 保持原字段，范围为 **1–100**。

| scope | countBy | Mini 达标条件 |
| --- | --- | --- |
| `user` | `shown` | 同一用户每天跨剧累计成功展示 N 次 |
| `user_drama` | `shown` | 同一用户每天在每部剧分别成功展示 N 次 |
| `user` | `completed` | 同一用户每天跨剧累计完整观看并结算 N 次 |
| `user_drama` | `completed` | 同一用户每天在每部剧分别完整观看并结算 N 次 |

“每部剧”按用户隔离。省略 `scope` 时默认 `user`，省略 `countBy` 时默认 `completed`。自然日使用应用配置时区。Mini 读取配置，决定广告触发、重拉、达标放行及 VIP 顺序；服务端保存事实、查询次数和结算奖励，不根据入剧次数拦截播放解析。请求不传计数模式或 N。

## 通用事实表

使用按用户桶路由的 `ad_shows_00` 至 `ad_shows_15`。每条记录只表达一次 SDK 成功展示，不保存 `context_json`、Offer、策略配置、N、门禁状态或任意业务扩展载荷。

| 字段 | 含义 |
| --- | --- |
| `id` | 物理表内自增主键，不占用户 UID 号段 |
| `bucket_id`、`application_id`、`visitor_id` | 认证主体与分片归属 |
| `event_id` | 一次成功展示的不可变幂等键，可复用广告 ClaimID |
| `scene` | 稳定用途编码，例如 `entry_reward`、`home_entry`、`vip_reward` |
| `ad_unit_id` | 当前应用登记、SDK 实际成功展示的公开广告位 |
| `drama_id`、`episode_id` | 可选内容来源；无剧目标时为 NULL |
| `occurred_at` | 首次成功确认该事实的请求在服务器入口固定的 UTC 接收时间 |

唯一索引为认证主体与 `event_id`；普通组合索引支持用户／场景／时间及用户／场景／剧目／时间。同键的场景、广告位和内容来源必须一致，冲突拒绝并保留原事实。重试沿用原记录时间，不因再次接收或客户端时间变化改日。剧集存在时，须同时提供剧目并验证所属及应用可见性；数据库无外键。

场景使用格式受限的字符串（小写字母开头，后续小写字母、数字、下划线，总长 1–64），不绑定奖励 Scene 枚举或奖励 Offer。新增首页等无内容场景直接使用稳定编码，无需加表或业务字段。

## 通用上报与查询

`POST /api/v1/me/ad-shows` 使用既有 VisitorToken：

```json
{
  "eventId": "一次成功展示的原幂等键",
  "scene": "entry_reward",
  "adUnitId": "官方广告位",
  "dramaId": "5008",
  "occurredAt": "2026-10-08T09:00:00.000Z"
}
```

`dramaId`、`episodeId` 为可选字符串。Handler 规范化和校验标识、场景、广告位长度及时间格式；旧 Mini 的 `occurredAt` 保留可解析，但不参与时间偏差拒绝或业务日归属。Service 固定服务器接收时间，校验广告位属于当前应用、可选内容存在及关联，再幂等保存。`entry_reward` 额外读取当前规则以校验按剧范围所需的剧目，写入沿用用户事务锁；达到 N 也必须保存新的有效事实。其他场景仍允许无内容目标。展示上报不解析奖励 Offer，不发放任何奖励。

`GET /api/v1/me/ad-shows?scene=home_entry` 查询当前认证用户的应用自然日展示事实，可追加 `dramaId`、`episodeId`。返回 `shownCount`、`progressDate`、`validUntil`，不含 N、计数模式或放行结论。`validUntil` 是下一应用当地午夜的 UTC 时刻。

### 首页例子

首页必须展示 N 次广告的假设使用 `scene=home_entry`，两个内容字段为空。Mini 从首页配置读取 N，查询当天次数，未达标时拉起官方广告；成功展示上报一条事实，广告退出后再次查询，关闭后未达标继续重拉，达标才挂载首页。展示失败不计数。首页、入剧和 VIP 按场景隔离，互不抵扣。

本例只用于验证通用表和 API，不新增首页广告开关、页面门禁或执行流程。相同基础能力也支持无剧目标的个人中心等场景。

## 入剧接口与执行

`GET /api/v1/me/entry-ad?dramaId=<字符串内部剧目ID>` 读取入剧配置与相应事实，返回 `enabled`、`scope`、`countBy`、`requiredCount`、`progressDate`、`validUntil`、`offer` 及所配置模式的计数。全局计数可省略剧目标；按剧计数需要当前可见剧目。零展示可省略 `shownCount`，Mini 按零解释。计数不按 N 截断，未查询的另一种计数为零，规则启用时提供 Offer，由 Mini 决定是否继续展示。

展示模式只读 `ad_shows_XX`，按 `entry_reward` 场景和可选剧目计数。完整观看独立读 `reward_grants_XX` 的入剧奖励事实；展示上报或展示存储失败不会阻止完播奖励结算与计数。入剧完整观看不发放分集或 VIP 权益。

入剧展示与完整观看写入沿用 MySQL 用户行锁及唯一键：每条通过校验的新事实都保存，重复键只恢复原记录。N 只决定是否继续要求用户观看广告，不作为事实写入上限。展示模式第 N 次成功展示入库后，该广告若完整结束，其完播也独立落账；提前关闭只记录已确认展示，不合成完播。按剧模式只汇总当前用户当天当前剧的事实，其他剧独立计数。查询返回实际次数，允许大于 N；Mini 以服务端次数 ≥ N 放行，进度文案最多显示 N/N，不在端上自行加一。

展示保存成功或幂等恢复均返回 `accepted: true`。入剧完播首次落账返回 HTTP 201、`status: granted` 和 `rewardType: entry_progress`，原键重试返回 HTTP 200、`status: already_granted`。响应以可选 `entryAdStatus` 返回请求所属日的最新进度；新版 Mini 清除待确认请求并直接使用该状态，仅旧响应缺少字段时补查。客户端继续接受旧服务端的 `entry_satisfied`，新服务端不再以此跳过有效事实。入剧完播不发放 VIP、分集权益或直接播放授权；VIP 和分集解锁的额度、发奖及幂等规则保持不变。

跨日处理：昨天已落库的原键今天重试，保留昨天的时间，回包给出今天的进度；昨天开始播放的广告今天首次到达服务器，按今天计数。接收后数据库处理跨过午夜仍按入口接收日归属。事实提交失败不能返回确认成功。同键替换业务目标依然拒绝。

Mini 未达标直接拉起官方广告，提前关闭后查询并自动重拉。展示模式提前关闭仍计一次；完整观看只有官方 `isEnded: true` 且奖励结算成功才计一次。加载失败、拉起失败及普通切后台不算展示。SDK show Promise 成功或 onClose 确认成功展示，同一广告只报一次，即使展示已达标也须等原生广告退出。

展示模式确认失败保留原事件、时间与来源，先补报再决定是否启动新广告。观看模式不等待展示确认，奖励使用原待领取队列恢复；展示模式也不因奖励结算故障丢失已确认进度。账号变化、切剧和跨午夜不能把旧归属或旧日进度用于新目标。

两种入剧策略同时开启时，先完成入剧广告，再执行 VIP 门禁，最终挂载播放器；已有 VIP 不跳过启用的入剧策略。

## 版本与数据库

2026-10-24 调整复用现有展示和奖励表，无新增数据库字段、表、状态缓存或迁移 SQL。接口路径及请求参数保持，旧 Mini 已支持的 `granted`／`already_granted` 合同继续适用；新 Mini 保留 `entry_satisfied` 和结算新增字段缺省时的兼容消费。先发布 Server，再发布 Mini。

后台统计仍读取原事实账本；升级后达标后的有效入剧完播也会计入广告结算数，但不会增加 VIP 或分集权益授予数。历史已落库事实不重写；升级前未保存的事实及其首次接收时间无法补回。

展示表由既有 `20261008_001_ad_shows.sql` 建立。新库仍按基线和全部增量初始化，已有库本次无需重复执行迁移；本地隔离测试不执行业务数据库变更。
