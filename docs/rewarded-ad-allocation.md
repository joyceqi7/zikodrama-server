# 激励广告位 UID 分配与旧 Mini 合同

## 配置与下发

- 在「应用管理」新增、编辑应用或列表内“广告位”配置中按行填写激励视频 code，允许 1–20 个；20 是本系统的配置上限，不代表 TikTok 官方限制。空行和重复项会清理，服务端按编码排序后分配。插屏仍配置一个 code。
- 配置继续保存在 MySQL 的应用广告位 JSON 中，无新增字段或数据库迁移。仅当前应用已配置的激励广告位参与入剧、逐集解锁和 VIP 规则。
- 服务端使用认证会话中的业务 UID（`visitorID`），按 `UID % 候选广告位数量` 得到从 0 开始的下标，每次返回一个广告位。入剧、逐集解锁、VIP 及领奖响应的 `nextAd.offer` 都采用此规则。
- UID 始终作为十进制字符串逐位取模，不转为浮点数或固定宽度整数；超过 JavaScript 安全整数和 `uint64` 上限也不会丢失精度。
- 候选集合不变时，同一 UID 在不同请求、规则、服务实例及重启后返回相同广告位，无须游标、Redis 或持久化用户分配记录。增加或删除候选会改变部分用户的映射；调整输入行顺序不会改变规范化后的顺序。
- 此方案分散不同用户的请求，不会让同一用户每次请求轮换广告位，也不能保证消除 TikTok `30001`。单用户连续请求仍需遵循平台频控。

## 旧 Mini 可用性

- Offer 继续使用单个字符串 `adUnitId`，领奖继续使用 `claimId`、`offerId`、`completedAdUnitId`、`isEnded` 等现有字段；无需版本标记、广告位数组或新接口。
- 领奖重新读取当前规则，校验完播编码属于该规则当前允许的激励集合且仍登记在当前应用；不要求完播编码与当前 UID 重新分配的结果相同。奖励类型、目标、限额、权限和幂等规则保持原语义。
- 旧 Mini 已缓存的 Offer 在其广告位仍有效时可以领取。删除广告位或停用规则会阻止新的领取；已成功的 `claimId` 仍优先恢复原结算事实。
- 记录实际完播广告位用于奖励流水和统计；生成下一个广告入口不会改写上一条流水。
- 旧 Mini 取消后重看可能复用同一个 Offer，同一 UID 本身也固定分配，不会每次 SDK 播放更换广告位。

## 新版 Mini 失败退避

- SDK 明确创建、回调注册、展示或错误回调失败后，同一个 SDK 容器的全屏广告共用 `adPolicy.retryDelayMs`（当前为 5 秒）。更换广告位或切换激励／插屏类型都不能绕过等待。
- 退避期内的点击不调用 SDK、不延长原期限，并记录 `ad_skipped` / `cooldown` 和结构化诊断日志。
- 正常完播、普通关闭和明确的用户取消不触发失败退避。结果未知时保留现有原生广告互斥，不能用超时解除互斥重拉。
- 旧 Mini 仍按自己的原退避逻辑运行。服务端可先发布；跨广告位退避需要新版 Mini 才能生效。

## 验证范围

聚焦测试覆盖三种奖励入口的单值合同、延迟领取和幂等、候选集合校验、实际广告位流水、连续广告选位、超长 UID 精度、跨实例及重启一致性，以及 Mini 的失败阶段、退避边界、取消和完播。使用测试替身，不调用真实 TikTok 服务；平台填充率、频控阈值及真机广告表现需在平台验收时确认。
