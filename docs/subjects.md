# 主体内容隔离与共享 VOD 空间

TikTok 标签目录及英文翻译仍全局共用，标签管理中的“关联短剧”只统计当前主体的编辑标签，包含未上线短剧，同主体应用不重复计数。切换主体重新读取统计并清除旧响应；缺少或不存在的主体不能读取关联统计。

每个应用固定绑定一个主体。主体独立维护短剧资料、分集、封面、视频、直连发布和 TikTok 官方发布；同主体应用共用内容。管理员、角色、权限定义和 TikTok 标签译名保持全局管理，应用登录、广告、用户及权益继续沿用应用边界。

| 数据或能力 | 范围 |
| --- | --- |
| 短剧草稿、分集、封面和视频 | 主体 |
| TikTok 发布方 | 主体 |
| VOD 空间 | 全局共享 |
| BytePlus 账号、AK/SK、地域、VOD AppID 和回调配置 | 全局配置 |
| 两渠道不可变版本、上线指针、审核、授权和发布记录 | 主体内短剧 |
| 两渠道轮播、热播、分类、排序、显隐和修订 | 主体 + 渠道 |
| 应用身份、广告位、用户和权益 | 应用 |
| 管理员、RBAC、标签译名 | 全局 |

## 后台与接口

所有主体共用全局 `media.space_name`，主体管理只维护名称及 TikTok 发布身份，不再单独配置 VOD 空间。共享空间名称为 3～40 位小写字母、数字或横线，首尾为字母或数字；在全局配置中维护。新上传和新官方发布使用共享空间，存量素材、发布快照和清理任务仍使用各自冻结的空间。短剧、分集、上传任务及发布权限继续按 `subject_id` 隔离，同空间不允许跨主体绑定封面或读取上传现场。TikTok 发布方身份已有资产后不能更换，同身份可以轮换密钥。

顶部主体切换会联动选择所属应用、清空旧列表与详情并作废旧响应。短剧、分集、上传和发布请求必须携带 `X-Subject-ID`；直接传入另一主体的主键也不能读取、修改、删除、绑定封面或发布。投放链接等应用级入口沿用应用头，由服务端解析主体；同时提供主体头时必须与应用归属一致。应用归属不能通过普通编辑移动。

新上传使用全局共享空间，分集保存自己的 VID，直连及官方发布使用同一套主体视频。没有共享源视频池、发布方目标 VID 池或自动跨主体复制功能。另一个主体要使用相同内容，需要独立建立资料并上传视频。

客户端直传授权恢复此前使用的官方 `GetUploadAuthWithExpiredTime`，沿用 SDK 默认的 `vod:ApplyUploadInfo`、`vod:CommitUploadInfo` 上传策略及配置有效期，不自行拼接 TRN。目标地域和共享空间仍来自全局媒资配置，短剧、分集和上传任务的业务访问继续按主体校验；上传不再额外要求账号 ID，官方视频登记仍需要该字段。用法见 [BytePlus Go SDK：生成临时上传凭据](https://docs.byteplus.com/en/docs/byteplus-vod/docs-go-sdk)。

剧目、链接、奖励报表及展示汇总按当前主体限制应用范围，“全部小程序”只指本主体内的应用。所有报表请求携带主体头，单应用筛选还携带应用头，两者必须匹配；缺少主体返回参数错误，不回退全局查询。切换主体重置报表的应用筛选、结果和明细，并忽略旧请求的迟到响应。

官方任务冻结发布身份、区域、账号和空间，恢复时不借用新配置；新的发布范围不复用另一范围的 Album。后台任务由持久化任务恢复主体，历史媒资任务使用其冻结空间。删除清理仍核对所有保留快照，迁移前共享的文件不能在其他主体仍有引用时删除。

## 已有数据升级

当前线上旧数据只有一个主体，执行合并脚本 `sql/migrations/20261105_001_subjects.sql`：创建主体表并插入 `id=1`，存量表新增 `subject_id NOT NULL DEFAULT 1`，相关发布及运营唯一键增加主体维度。后续新主体从空内容开始，查询和写入使用可信主体上下文，不以默认值绕过应用归属或权限检查。

旧剧集主键、VID、发布版本、线上指针、投放及权益引用保持不变。原发布方配置和 VOD 空间复制给默认主体，`global_configs` 的所有原记录及已有字段值保留；只在媒体账号字段缺失时从旧发布配置补充，共享空间增量完成后上传只读取全局空间。原 `dramas.published_snapshot`、`dramas.platform_album_id` 和 `episodes.platform_episode_id` 保留原值并在列注释标记已废弃；迁移只复制一次历史发布数据，运行时查询和保存排除这些原列，官方状态改从主体发布记录及冻结快照读取。无需拆分内容、重写 ID 或运行额外命令。

脚本在冻结基线及全部前序增量之后执行一次；执行前备份并停止旧 API/Worker，完成后配套更新 Server/Admin。已经执行过原四份主体增量的库不重跑合并脚本，也不因代码清理而重新迁移原数据。消费 API、VisitorToken、UID/分片、播放器许可、广告位及奖励合同保持不变，Mini 无需改包；不得清空 UID 发号缓存。

## 验收与回退

- 核对默认主体原 ID、VID、应用身份、通道修订、线上指针及用户凭据不变。
- 核对存量数据全部归属默认主体 `id=1`，剧集数量及原有发布、活动和权益关联不变。
- 用旧 Mini 请求及旧 Token 验证启动、更多、首页、详情、旧链接、相邻集播放及权益。
- 验证两主体的列表、直接主键操作、分集、封面绑定、上传任务及发布互相隔离；同主体多应用继续共用内容。
- 验证不同主体共用全局空间、缺少全局空间时拒绝新上传、旧表单不能覆盖共享空间、历史任务冻结空间保持不变。

自动化使用平台替身，不会提交真实送审。验证命令为 `make verify`、`make test-integration-local` 和 Admin 的 `npx pnpm@11.11.0 verify`，界面另检查桌面与移动视口。迁移涉及结构和业务引用变化，回退必须成套恢复数据库备份与旧镜像，不能只替换二进制。

共享空间升级：已完成主体统一升级的库再执行 `20261106_001_shared_vod_space.sql`，移除空间独占唯一键并将主体空间原列标记废弃，保留原值。直接沿用原全局媒资配置，不改写任何配置值。运行时不再读写主体空间列，旧后台提交的 `vodSpaceName` 忽略；新后台在全局媒资配置编辑共享空间。
